01

Drei Dinge, die eine handgebaute XML-Datei am häufigsten ungültig machen.

Eine pain.001-XML von Hand in einem Texteditor oder einer Excel-Formel zu bauen, ist möglich, aber eine Kleinigkeit genügt, und die Bank lehnt die Datei ohne Erklärung ab.

  1. Spalten werden anhand des Namens erkannt, nicht der Reihenfolge.

    Der Generator sucht automatisch nach Spaltenüberschriften wie „IBAN“, „Betrag“, „Name“, auf Slowakisch, Englisch oder Deutsch. Bei einem ungewöhnlichen Excel prüfen Sie die Zuordnung und korrigieren Sie sie bei Bedarf manuell in den Auswahlfeldern über der Vorschau.

  2. VS/SS/KS haben in der XML kein eigenes Feld.

    Sie müssen in genauer Reihenfolge /VS.../SS.../KS... in EndToEndId geschrieben werden (das Länderprofil „sk“ erledigt das automatisch). Das Profil „de“ verzichtet ganz auf VS/SS/KS und nutzt stattdessen einen unstrukturierten Verwendungszweck, da deutsche Banken diese slowakischen Referenzsymbole nicht verwenden.

  3. Das Format ist die eine Sache, die Regeln der Bank die andere.

    Nach der Erstellung läuft dieselbe Engine wie bei SEPA pain.001 Doctor über die Datei: BIC, Ausführungsdatum, Sonderzeichen und das Transaktionslimit der gewählten Bank.

03

Zwei Funktionen. Zahlungen hinein, XML heraus, sofort geprüft.

Kein Server, kein API-Schlüssel, keine Anmeldung. generator-pain001.js ist reines JavaScript: lesen, forken oder im eigenen Code bzw. in der CI ausführen.

generator-pain001.js 0 Abhängigkeiten 
import { parseRows, mapColumns, buildXml } from './generator-pain001.js';
import { diagnose } from './doctor-pain001.js';
// oder global: const { parseRows, mapColumns, buildXml, bicFromIban } = window.SepaGenerator;

const rows = parseRows(excelRows);
const { payments } = mapColumns(rows, undefined, profile);

const xml = buildXml({
  bank:     'tatrabanka' | 'slsp' | 'vub' | 'csob' | 'generic',
  profile:  'sk' | 'de',  // 'de': Verwendungszweck statt VS/SS/KS
  payer:    { name, iban, bic },
  execDate: '2026-09-06',  // Standard: morgen
  msgId:    undefined,       // default: auto ARL-YYYYMMDD-HHMMSS
  payments,       // {iban, amount, name, vs, ss, ks, message, bic, endToEndId, dateIso}[]
});

// die Datei wird sofort mit derselben Engine wie SEPA pain.001 Doctor geprüft:
const report = diagnose({ xml, bank: 'tatrabanka' });

Das Parsen von Excel/CSV, die Spaltenzuordnung und der Aufbau der XML laufen genau so, wie das Formular oben sie aufruft, in Ihrem Browser. Es gibt kein Backend und keinen API-Schlüssel, der den Inhalt Ihrer Zahlungen woandershin übertragen könnte.

Reihenfolge und Pflicht-/Optional-Status jedes XML-Felds stammen direkt aus der technischen Dokumentation der Tatra banka (pain.001.001.03, Abschnitte GroupHeader und PaymentInformation) sowie denselben bankspezifischen Regeln, die SEPA pain.001 Doctor prüft.

Kostenlos, offen, ohne Werbung und ohne Tracking über anonyme Nutzungszahlen hinaus. Verarbeitet der Generator einen Fall falsch, melden Sie ihn bitte als Issue auf GitHub.

06

Fragen, die wirklich gestellt werden.

Direkte Antworten zur Erstellung einer SEPA-pain.001-Datei aus Excel.

Wie bereite ich Excel vor, damit der Generator es liest?

Markieren Sie die Spalten IBAN, Betrag und Empfängername (idealerweise mit Kopfzeile in der ersten Zeile) und kopieren Sie die Zellen direkt in das Textfeld (Strg+C, Strg+V): Excel fügt sie tabulatorgetrennt ein, und der Generator erkennt das automatisch, bei slowakischen, englischen oder deutschen Spaltenüberschriften. Genauso funktioniert ein CSV-Export mit Semikolon oder Komma, oder das direkte Hochladen einer .csv-/.txt-/.tsv-Datei. Erkennt die automatische Spaltenerkennung ein Feld falsch, korrigieren Sie es manuell in den Auswahlfeldern über der Zahlungsvorschau.

Wo landet der Verwendungszweck (VS/SS/KS) in der SEPA-XML?

pain.001.001.03 hat kein eigenes Feld für den slowakischen variabilný/špecifický/konštantný symbol. Im Profil „Slowakei“ schreibt der Generator diese als /VS.../SS.../KS... in PmtId/EndToEndId, genau nach der Konvention der Národná banka Slovenska, die auch das Schwester-Tool SEPA pain.001 Doctor prüft. Im Profil „Deutschland (DK)“ gibt es diese drei Felder gar nicht: Der Text steht in RmtInf/Ustrd (Verwendungszweck), und EndToEndId wird aus einer eigenen zugeordneten Spalte übernommen oder ist „NOTPROVIDED“, wenn sie leer bleibt.

Wie importiere ich die XML in mein Online-Banking?

Laden Sie die heruntergeladene .xml-Datei im Online-Banking im Formular für Sammel-/Stapelüberweisungen hoch (meist unter Zahlungen → Sammelüberweisungen → Datei importieren). Das funktioniert bei Tatra banka, SLSP, VÚB und ČSOB genauso wie bei deutschen, österreichischen und Schweizer Banken (zum Beispiel Sparkasse, Volksbank, Deutsche Bank, Commerzbank, Raiffeisen, Erste, UBS oder PostFinance); der genaue Ort unterscheidet sich je Bank. Schlägt der Import fehl, prüfen Sie zuerst den SEPA-pain.001-Doctor-Bericht, der direkt nach der Erstellung angezeigt wird: Er zeigt genau das Element, das eine Bank ablehnen wird.

Werden meine Zahlungsdaten irgendwohin gesendet?

Nein. Das Parsen von Excel und die XML-Erstellung laufen vollständig im Browser. IBANs, Beträge und Namen werden nie gesendet; das Tool hat kein Backend. Die einzige Netzwerkaktivität ist das Laden der statischen Seitendateien und ein anonymer Nutzungszähler (Umami), der nur erfasst, dass eine Erstellung stattfand und wie das Prüfergebnis ausfiel, nie den Inhalt der Zahlungen.

Wie viele Zahlungen dürfen in einer Datei sein?

Der Generator verarbeitet maximal 5000 Zahlungen auf einmal. Haben Zahlungen unterschiedliche Ausführungsdaten, teilt der Generator sie automatisch nach Datum in separate PmtInf-Blöcke auf; Tatra banka begrenzt einen solchen Block trotzdem auf 500 Transaktionen, worauf SEPA pain.001 Doctor nach der Erstellung hinweist.

Warum hat die Bank die Datei trotz Prüfung abgelehnt?

SEPA pain.001 Doctor prüft öffentlich dokumentierte Format- und bankspezifische Regeln, nicht den Status Ihres Kontos, ob das Empfängerkonto existiert, oder interne Limits der Bank (z. B. ein Tageslimit für Überweisungen). Ein sauberes Prüfergebnis ist daher keine Garantie für die Annahme. Lehnt eine Bank die Datei trotzdem ab, prüfen Sie zuerst den genauen Fehlertext im Online-Banking.

Gespeicherte Zahlerprofile (IBAN, BIC, Bank mit einem Klick), Erstellung mehrerer Zahlungsdateien gleichzeitig, voreingestellte Vorlagen für Spaltenzuordnung für Pohoda, Omega (KROS) und Money S3, einen Verlauf der letzten 50 erstellten Aufträge mit erneutem Download und bevorzugten E-Mail-Support. Wie unterscheidet sich das Profil „Deutschland (DK)“ von „Slowakei“?

Das Profil „Deutschland (DK)“ (Deutsche Kreditwirtschaft, die im deutschen Bankwesen geltenden pain.001.001.03-Regeln) blendet die Spalten VS/SS/KS aus und bietet stattdessen einen freien Verwendungszweck (max. 140 Zeichen, SEPA-Zeichensatz) sowie eine optionale EndToEndId-Spalte. Die Bankliste reduziert sich auf eine generische Vorlage „Bank nach DK-Regelwerk (pain.001.001.03)“ statt der vier slowakischen Banken, da die bankspezifischen Regeln von Tatra banka/SLSP/VÚB/ČSOB dafür nicht gelten. Der BIC bleibt optional, wie bei jeder IBAN aus einem EWR-/SEPA-Land.
